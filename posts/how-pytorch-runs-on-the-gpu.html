How PyTorch runs on the GPU

Ketan Suhaas Saichandran
gpupytorchcuda

Builds on: The CUDA programming model, Autograd in PyTorch · Leads to: Kernel fusion and torch.compile

A line like y = x @ w never runs on the GPU itself. It travels down a stack and ends as a kernel queued on a stream, and the CPU moves on at once.

The stack

Python asks; the dispatcher routes by device and dtype; a library kernel does the math; the launch hands it to the GPU.

Example

opts = dict(device="cuda", dtype=torch.bfloat16)
x = torch.randn(4096, 4096, **opts, requires_grad=True)
w = torch.randn(4096, 4096, **opts)
y = x @ w           # CUDA + bf16 -> cuBLAS GEMM, queued
print(y.grad_fn)    # <MmBackward0>: autograd recorded the backward

Launches are asynchronous

The CPU only enqueues kernels on a stream and runs ahead. The GPU drains the queue in order. They meet only when the CPU needs a value.

Timing it right

A wall clock around async code measures how fast the CPU queued work, not how long the GPU took.

t0 = time.perf_counter(); y = x @ w
t1 = time.perf_counter()        # wrong: only the launch

s, e = (torch.cuda.Event(enable_timing=True) for _ in range(2))
s.record(); y = x @ w; e.record()
torch.cuda.synchronize()
print(s.elapsed_time(e), "ms")  # right: GPU time between the events

Example

The $4096\times4096$ by $4096\times4096$ matmul: $4096^2$ outputs, each $4096$ multiply-adds, and its intensity in bf16 is $n/3$ (roofline):

$$F=2\cdot4096^3\approx1.37\times10^{11}\ \text{FLOP},\qquad I=\frac{4096}{3}\approx1365\gt156\ \Rightarrow\ \text{compute-bound}.$$

So the roofline time is the math term, with A100 bf16 peak ~312 TFLOP/s (approximate spec):

$$t\ \ge\ \frac{1.37\times10^{11}}{3.12\times10^{14}}\approx0.44\ \text{ms}.$$

The wrong timer reports only the CPU's launch work, tens of microseconds. Warm up first: the first call pays one-time setup.

Small ops are launch-bound

Each op costs a few microseconds of CPU work (Python, dispatcher, driver) no matter how small the tensor. If the kernel is shorter than that, the GPU waits for the CPU.

CPU and GPU form a two-stage pipeline: the CPU issues op $k+1$ while the GPU runs op $k$. In a pipeline, the steady-state time per item is the slower stage. For an elementwise op the GPU stage is memory-bound (roofline), so it is bytes over bandwidth:

$$t_{\text{op}}\approx\max\big(t_{\text{launch}},\ \tfrac{\text{bytes}}{\text{bandwidth}}\big),\qquad t_{\text{launch}}\sim 5\ \mu\text{s}\ \text{(measured, approximate)}.$$

Example: fp32 add, A100 (~2 TB/s)

out = x + y on $N$ elements reads two floats and writes one: $12N$ bytes.

The crossover is where the two terms of the max are equal:

Below about a million elements, an elementwise op is paying for the launch, not the data.

Memory: the caching allocator keeps freed GPU blocks and reuses them instead of calling cudaMalloc each time, so nvidia-smi shows memory_reserved(), not memory_allocated().

Work it out yourself

for i in range(10_000): x = x * 1.0001 + 0.001 on a CUDA tensor of 1000 floats takes ~0.1 s. Why, and what helps?

Solution

Each step is two ops (*, then +), each a kernel. Each kernel reads and writes 1000 floats:

$$t_{\text{gpu}}=\frac{2\cdot1000\cdot4\ \text{B}}{2\times10^{12}\ \text{B/s}}=4\ \text{ns}\ \ll\ t_{\text{launch}}\approx5\ \mu\text{s}.$$

So by the max formula every op costs $t_{\text{launch}}$:

$$\underbrace{2\times10^{4}}_{\text{launches}}\times5\times10^{-6}\ \text{s}=0.1\ \text{s}.$$

Pure launch overhead: the GPU is busy for only $2\times10^4\cdot4$ ns $=80\ \mu$s of it.

BatchingIf the items are independent, stack them into one big tensor: one launch does all the work.
FusionOne kernel for x * a + b halves the launches: $10^4\times5\ \mu$s $=0.05$ s (torch.compile).
CUDA graphsRecord the launch sequence once, replay it with one call: the per-kernel CPU cost disappears (torch.cuda.CUDAGraph, or torch.compile(mode="reduce-overhead")).
