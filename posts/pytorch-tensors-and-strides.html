Tensors: shape, dtype, device, and strides

Ketan Suhaas Saichandran

Builds on: Reading the notation in papers, Four views of matrix multiplication · Leads to: Broadcasting and einsum

A tensor is a flat row of numbers in memory plus a small recipe for reading it as an array. Many operations rewrite only the recipe.

Step 1: the address rule

Memory is one line, so an array needs a rule that turns an index tuple into a position on that line. PyTorch's default is row-major: lay the rows end to end.

In the $2\times3$ example, to reach $[i,j]$ you skip $i$ whole rows of $3$ elements, then $j$ more:

$$\text{offset}(i,j)=i\cdot3+j\cdot1 \quad\Rightarrow\quad (s_0,s_1)=(3,1).$$

Call the multipliers strides and allow the tensor to begin partway into the buffer. For $d$ axes:

$$\boxed{\ \text{offset}(i_0,\dots,i_{d-1})=\text{start}+\sum_{k=0}^{d-1}i_k\,s_k\ }$$

Row-major strides follow from the same skipping argument. One step along axis $k$ jumps over one whole block of all the later axes:

$$s_{d-1}=1,\qquad s_k=n_{k+1}\,s_{k+1}=\prod_{l\gt k}n_l.$$

Check on $(2,3)$: $s_1=1$, $s_0=3\cdot1=3$. ✓ Byte address $=$ offset $\times$ bytes per element: x[1, 2] is offset $1\cdot3+2\cdot1=5$, byte $5\cdot4=20$ in fp32.

Step 2: transpose and slice rewrite only the recipe

Write each element of the new tensor as an element of the old one, plug it into the address rule, and read off the new strides. No data moves.

Transpose. $y=x^T$ means $y[i,j]=x[j,i]$, so

$$\text{offset}_y(i,j)=\text{offset}_x(j,i)=j\,s_0+i\,s_1$$

$$=i\,\underbrace{s_1}_{\text{new }s_0}+j\,\underbrace{s_0}_{\text{new }s_1}\quad\Rightarrow\quad\text{strides }(1,3).$$

Check: x.T[2, 1] is at $2\cdot1+1\cdot3=5$, the same element as x[1, 2]. ✓

Slice. $y=x[:,1{:}]$ means $y[i,j]=x[i,j+1]$, so

$$\text{offset}_y(i,j)=i\,s_0+(j+1)\,s_1=\underbrace{s_1}_{\text{new start}}+i\,s_0+j\,s_1.$$

Start moves to $s_1=1$, strides stay $(3,1)$, shape becomes $(2,2)$. In general a slice a:b:c on axis $k$ reads $x[\dots,a+c\,i,\dots]$, so start $\mathrel{+}=a\,s_k$ and $s_k\leftarrow c\,s_k$.

x = torch.arange(6.).view(2, 3)
x.stride()                  # (3, 1)
x.T.stride()                # (1, 3)   same storage
x[:, 1:].stride()           # (3, 1)   shape (2, 2)
x[:, 1:].storage_offset()   # 1        starts one element in
x.T.data_ptr() == x.data_ptr()   # True: no copy

Step 3: contiguous, and why .view can fail

.view never copies: it must find new strides that address the same bytes. Merging two axes into one is possible only if the inner axis ends exactly where the outer axis steps.

Merge axes $k,k+1$ (sizes $n_k,n_{k+1}$) into one axis with a single stride $s$. Merged index $m=i\,n_{k+1}+j$ must hit the same element as $(i,j)$:

$$(i\,n_{k+1}+j)\,s=i\,s_k+j\,s_{k+1}\qquad\text{for all } i,j.$$

$$(i,j)=(0,1):\ s=s_{k+1};\qquad (i,j)=(1,0):\ s_k=n_{k+1}\,s_{k+1}.$$

So .view(-1) (merge every axis) works exactly when $s_k=n_{k+1}s_{k+1}$ for all $k$. Add $s_{d-1}=1$ and these are the row-major strides of Step 1: that is the definition of contiguous. (Axes of size $1$ are exempt: their index is always $0$, so their stride never matters.)

x.T: shape $(3,2)$, strides $(1,3)$. Need $s_0=n_1s_1=2\cdot3=6$, have $1$. ✗ Listing its offsets in row-major order shows why no single stride exists:

$$\underbrace{0,3}_{i=0},\ \underbrace{1,4}_{i=1},\ \underbrace{2,5}_{i=2}\qquad\text{jumps } +3,-2,+3,-2,+3.$$

So .view(6) errors, .reshape(6) copies those values in that order, and .contiguous() writes a fresh $(3,2)$ buffer with row-major strides $(2\cdot1,\,1)=(2,1)$.

x.T.is_contiguous()         # False: stride (1, 3), not (2, 1)
x.T.view(6)                  # RuntimeError: use .reshape(...)
x.T.reshape(6)               # tensor([0., 3., 1., 4., 2., 5.])  copies
x.T.contiguous().stride()    # (2, 1): fresh row-major buffer

dtype: bytes per number

Memory and bandwidth scale with bytes per element. Halving the dtype halves both.

Bytes $=$ bits$/8$: float32 is $32/8=4$, the 16-bit types are $2$, int64 is $8$. A tensor's footprint is

$$\text{bytes}=\texttt{numel}\times\texttt{element\_size}=\Big(\prod_k n_k\Big)\times\frac{\text{bits}}{8}.$$

dtypeBytesTypical use

Example

$10^9$ parameters: $10^9\times4\text{ B}=4$ GB in fp32, $10^9\times2\text{ B}=2$ GB in bf16. Check any tensor with x.element_size() * x.numel().

Where the ranges come from (bit layouts in Floating point and mixed precision). A float is $1.f\times2^{e-\text{bias}}$. fp16 has 5 exponent bits (bias $15$, top usable field $30$) and 10 mantissa bits, so its largest value is

$$(2-2^{-10})\cdot2^{30-15}=2^{16}-2^{5}=65504.$$

bf16 keeps fp32's 8 exponent bits (bias $127$), so the same range, about $(2-2^{-7})\cdot2^{127}\approx3.4\times10^{38}$, but only 7 mantissa bits instead of 23: fewer digits.

device: moving is a copy

Operands must live on the same device. .to('cuda') allocates GPU memory and copies the bytes over PCIe.

x = torch.randn(4096, 4096)                # CPU, 64 MiB fp32
y = x.to('cuda')                           # new storage on the GPU
z = x.to('cuda', dtype=torch.bfloat16)     # copy + cast: 32 MiB
x + y                                      # RuntimeError: different devices

Size. $4096=2^{12}$, so

$$2^{12}\cdot2^{12}=2^{24}\text{ elements}\times4\text{ B}=2^{26}\text{ B}=64\text{ MiB}\approx67.1\text{ MB}.$$

In bf16, $2^{24}\times2\text{ B}=32$ MiB. Time $=$ bytes $/$ bandwidth, using approximate specs (PCIe 4.0 x16 about 25 GB/s in practice; A100 HBM about 2 TB/s):

$$\text{PCIe: }\frac{67.1\times10^6}{25\times10^9}\approx2.7\text{ ms},\qquad \text{HBM: }\frac{67.1\times10^6}{2\times10^{12}}\approx34\ \mu\text{s}.$$

The host link is about $2.7\text{ ms}/34\ \mu\text{s}\approx80\times$ slower than the GPU reading its own memory. Move data once, not every step.

Work it out yourself

x = torch.zeros(4, 5). Predict shape, stride and storage offset of x.T and x[:, 1:]. Which of the three can call .view(-1)?

Solution

x: row-major (Step 1), $s_1=1$, $s_0=n_1s_1=5$.

x.T: swap the strides (Step 2), $(1,5)$, shape $(5,4)$. Contiguous needs $s_0=n_1s_1=4\cdot5$; it is $1$. ✗

x[:, 1:]: start $+=1\cdot s_1=1$, strides unchanged $(5,1)$ (Step 2). Merge test (Step 3): $s_0=n_1s_1=4\cdot1=4$, but $s_0=5$. ✗ Its offsets run $1,2,3,4,\ 6,\dots$: the jump of $2$ skips column 0 of the next row.

x(4, 5)(5, 1)0yes
x.T(5, 4)(1, 5)0no
x[:, 1:](4, 4)(5, 1)1no: row-major would be (4, 1)

Check: x[:, 1:][2, 3] is at $1+2\cdot5+3=14=2\cdot5+4$, i.e. x[2, 4]. ✓ Only x can .view(-1); the other two need .reshape(-1), which copies.
