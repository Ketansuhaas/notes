Datasets and DataLoaders

Ketan Suhaas Saichandran
pytorchdata-loading

Builds on: Optimizers and their memory, Expectation and variance algebra · Leads to: Why GPUs: latency vs. throughput

The Dataset knows single examples. The DataLoader turns them into a stream of shuffled batches, fast enough to keep the GPU busy.

Dataset: one example at a time

Two methods: how many examples, and give me example $i$. Nothing about batches or order.

from torch.utils.data import Dataset, DataLoader
class Squares(Dataset):
    def __init__(self, n): self.x = torch.arange(n, dtype=torch.float32)
    def __len__(self): return len(self.x)
    def __getitem__(self, i): return self.x[i], self.x[i] ** 2

DataLoader: the batching pipeline

Pick indices, fetch examples in parallel, stack them into one batch, stage it for a fast copy to the GPU.

loader = DataLoader(Squares(1000), batch_size=64, shuffle=True,
                    num_workers=4, pin_memory=True, drop_last=False)
x, y = next(iter(loader))                 # x, y: (64,)
x = x.to('cuda', non_blocking=True)       # async copy from pinned memory
shuffle=Truenew random order every epoch
collate_fnlist of examples → batch (default: stack each field)
num_workersprocesses calling __getitem__ in parallel with training
pin_memorypage-locked host memory: faster, asynchronous copies to the GPU
drop_lastskip the final short batch

Shape (64,). Each __getitem__ returns a pair of 0-d tensors $(x_i,\,x_i^2)$. The default collate stacks field by field over the $64$ sampled indices $i_1,\dots,i_{64}$:

$$x=\operatorname{stack}(x_{i_1},\dots,x_{i_{64}})\in\mathbb R^{64},\qquad y=\operatorname{stack}(x_{i_1}^2,\dots,x_{i_{64}}^2)\in\mathbb R^{64}.$$

How many workers. One worker builds a batch in $B\,t_{\text{item}}$. With $w$ workers in parallel a batch is ready every $B\,t_{\text{item}}/w$, and the GPU never waits if that is at most one training step:

$$\frac{B\,t_{\text{item}}}{w}\le t_{\text{step}}\quad\Rightarrow\quad w\ge\frac{B\,t_{\text{item}}}{t_{\text{step}}}.$$

Illustrative numbers: $B=64$, $2$ ms to decode and augment an image, $40$ ms per step gives $w\ge64\cdot2/40=3.2$, so $4$ workers.

Why pinned. (Hardware fact.) The GPU's copy engine reads host memory directly only if the OS cannot page it out. From ordinary memory the driver first copies into a pinned staging buffer, then to the GPU; pinning skips that extra copy and lets non_blocking=True overlap the transfer with compute.

Why shuffle

SGD needs each mini-batch gradient to be an honest, noisy estimate of the full gradient. Random batches give that; sorted data does not.

The full-data loss and a batch estimate of its gradient:

$$L=\frac1N\sum_{i=1}^N\ell_i,\qquad \hat g_B=\frac1B\sum_{m=1}^{B}\nabla\ell_{I_m},$$

where $I_1,\dots,I_B$ are the indices the sampler put in this batch.

Step 1: every slot is a uniform draw. shuffle=True draws a uniformly random permutation $\pi$ of $1..N$ and cuts it into consecutive batches, so $I_m=\pi(p)$ for some fixed position $p$. Permutations with $\pi(p)=i$ number $(N-1)!$ out of $N!$, so

$$P(I_m=i)=\frac{(N-1)!}{N!}=\frac1N\qquad\text{for every } i.$$

Step 2: so the batch gradient is unbiased. Linearity of expectation, then Step 1:

$$\mathbb E[\hat g_B]=\frac1B\sum_{m=1}^B\mathbb E[\nabla\ell_{I_m}]=\frac1B\sum_{m=1}^B\sum_{i=1}^N\frac1N\nabla\ell_i$$

$$=\frac1B\cdot B\cdot\nabla L=\nabla L.$$

This holds for every batch, including a short last one.

Step 3: its noise shrinks like $1/B$. Per coordinate, let $X_m=\nabla\ell_{I_m}$ and $\sigma^2=\tfrac1N\sum_i(\nabla\ell_i-\nabla L)^2$, the spread of single-example gradients. If the $X_m$ were independent (sampling with replacement), variances add (variance algebra):

$$\operatorname{Var}(\hat g_B)=\frac1{B^2}\sum_{m=1}^B\operatorname{Var}(X_m)=\frac{B\sigma^2}{B^2}=\frac{\sigma^2}{B}.$$

A permutation samples without replacement, which adds a covariance $c$ between any two slots. Find it from the case $B=N$, where the batch is the whole dataset and its sum never changes:

$$0=\operatorname{Var}\Big(\sum_{m=1}^NX_m\Big)=N\sigma^2+N(N-1)\,c\ \Rightarrow\ c=-\frac{\sigma^2}{N-1}.$$

$$\operatorname{Var}(\hat g_B)=\frac{B\sigma^2+B(B-1)c}{B^2}=\frac{\sigma^2}{B}\cdot\frac{N-B}{N-1}.$$

For $N=50{,}000$, $B=64$ the factor is $49{,}936/49{,}999\approx0.999$: $\operatorname{Var}\approx\sigma^2/B$.

Example: sorted data breaks Step 1

MNIST's training set has $5{,}923$ zeros, sorted first. $5923/64\approx92.5$, so the first $92$ batches are all "0"s. Nothing is random: that batch gradient is the class-0 gradient every time, while the full gradient mixes all classes by their share $N_c/N$:

$$\hat g_B=\nabla L_0\ \ne\ \nabla L=\sum_{c=0}^{9}\frac{N_c}{N}\nabla L_c.$$

Every step pushes toward predicting 0, then toward 1, and so on: the model chases the latest class.

Work it out yourself

$N=50{,}000$ examples, batch_size=64. How many optimizer steps per epoch with drop_last=False and with drop_last=True? How big is the last batch, and why might you drop it?

Solution

Divide with remainder, $N=qB+r$ with $0\le r\lt B$: there are $q$ full batches and, if $r\gt0$, one short batch of $r$.

$$\texttt{drop\_last=False}:\ q+[r\gt0]=\lceil N/B\rceil;\qquad \texttt{drop\_last=True}:\ q=\lfloor N/B\rfloor.$$

Here $64\cdot781=49{,}984$ and $50{,}000-49{,}984=16$, so $q=781$, $r=16$:

$$\texttt{False}:\ 782\text{ steps, the last of }16;\qquad \texttt{True}:\ 781\text{ steps}.$$

The $16$ dropped examples are the last $16$ positions of a fresh random permutation, so by Step 1 each example is dropped with probability $16/50{,}000=0.032\%$ per epoch: different ones each epoch, nothing permanently skipped.

Why drop: by Step 3 a batch of $16$ has variance $\sigma^2/16=4\cdot\sigma^2/64$, $4\times$ that of a full batch. BatchNorm statistics over $16$ examples are noisy too, and every batch keeping the same shape helps compiled code.
