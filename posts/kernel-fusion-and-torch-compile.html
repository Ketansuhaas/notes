Kernel fusion and torch.compile

Ketan Suhaas Saichandran
gpupytorchkernel-fusiontorch-compile

Builds on: Arithmetic intensity and the roofline, How PyTorch runs on the GPU · Leads to: Triton: programming GPUs in blocks

Elementwise ops do almost no math per byte, so HBM traffic sets their speed. Fuse a chain into one kernel: intermediates stay in registers, and only the input and output touch memory.

Unfused: one HBM round trip per op

Each PyTorch op is its own kernel. It reads its input from HBM and writes its result back, even if the next op immediately reads it again.

$$y=\operatorname{gelu}(x\odot w+b),\qquad \underbrace{x}_{N},\ \ w,b \text{ small (broadcast per feature)}.$$

Bytes moved, tied to the roofline

Far below the ridge point, time is just bytes over bandwidth. So the speedup is the traffic ratio.

$$t\approx\frac{\text{bytes}}{\text{BW}},\qquad \text{speedup}\approx\frac{\text{bytes}_{\text{unfused}}}{\text{bytes}_{\text{fused}}}=\frac{6N}{2N}=3.$$

Example: $x$ is $8192\times8192$ BF16 (134 MB), A100 (~2 TB/s)

HBM trafficTime
Unfused (3 kernels)$6\times134\approx805$ MB~0.40 ms
Fused (1 kernel)$2\times134\approx268$ MB~0.13 ms

Still memory-bound: a few FLOPs per element over 4 bytes is well below even the non-tensor-core ridge (~10 FLOP/byte on A100).

torch.compile does it for you

You keep writing eager PyTorch. The compiler captures the graph, finds fusable ops, and writes the fused kernel.

import torch, torch.nn.functional as F
x = torch.randn(8192, 8192, device="cuda", dtype=torch.bfloat16)
w = torch.randn(8192, device="cuda", dtype=torch.bfloat16)
b = torch.randn(8192, device="cuda", dtype=torch.bfloat16)

def f(x, w, b):
    return F.gelu(x * w + b)

f_c = torch.compile(f)   # compiles on first call, then reuses
y = f_c(x, w, b)         # one fused Triton kernel instead of three
TorchDynamoReads the Python bytecode as it runs and records the torch ops into a graph.
AOTAutogradTraces the matching backward graph too, so training gets fused.
TorchInductorFuses ops and generates code: Triton kernels on GPU, C++/OpenMP on CPU.

Graph break: code Dynamo cannot trace (a print, data-dependent Python control flow, an unsupported call) splits the graph there and runs in plain Python. No fusion crosses a break.

Matmuls usually still go to cuBLAS. The win is in the elementwise and reduction glue around them.

Work it out yourself

A chain of $k$ unary elementwise ops on $N$ elements. Unfused vs fused HBM traffic? For $k=5$, $N=10^8$ BF16 on an A100, how long does each take? When would fusing more ops stop helping?

Solution

Unfused: each op reads $N$ and writes $N$: $2kN$. Fused: read once, write once: $2N$. Ratio $k$.

$k=5$: unfused $2\cdot5\cdot10^8\cdot2$ B $=2$ GB $\to$ ~1 ms. Fused $0.4$ GB $\to$ ~0.2 ms.

The ratio holds while the fused kernel stays memory-bound. Once its FLOPs per byte pass the ridge point, compute sets the time and fusing more ops stops paying off.
